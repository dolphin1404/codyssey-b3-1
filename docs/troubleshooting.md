# CLIP-IT 트러블슈팅 보고서

## 사례 1. 홈은 열리지만 `/health`가 404를 반환

실행 환경: **2026-10-03 로컬 Docker / Nginx 프록시 재현**. 이미 확보한 실제 로컬 기록이며 EC2에서 발생한 장애 기록은 아닙니다.

| 단계 | CLIP-IT에서 확인한 내용 |
| --- | --- |
| 증상 | 홈을 프록시하는 Nginx에서 홈은 200이지만 `http://127.0.0.1:18081/health`가 404와 HTML을 반환했습니다. |
| 가설 | `/health` 전용 처리 없이 원본 Vercel에 요청을 전달해 원본에 없는 경로까지 전달되었습니다. |
| 검증 | 전용 location이 없는 초기 프록시와 수정한 컨테이너를 별도 포트에서 실행하고 같은 요청의 상태·본문·로그를 비교했습니다. |
| 조치 | exact-match `location = /health`에서 `default_type text/plain; return 200 "OK\n";`으로 직접 응답하게 했습니다. |
| 결과 | 수정 후 `http://127.0.0.1:18080/health`는 200 / `text/plain` / `OK`, 홈은 200을 유지했습니다. |
| 재발 방지 | 외부와 SSH 내부 `/health`의 상태·본문 검사를 배포에 포함하고 홈 접속과 EC2 자체 헬스체크를 각각 확인합니다. |

원본 근거: [20261003-local-troubleshooting.json](evidence/20261003-local-troubleshooting.json). 최종 경로 설정 검증은 [20261003-local-validation.json](evidence/20261003-local-validation.json)에 있습니다.

현재 설정은 공개 홈·작품 목록·정적 파일만 프록시하고 나머지 경로는 고정 HTTPS 원본으로 이동합니다. 위 사례의 초기 전체 프록시와 최종 설정을 구분하며, 최종 `/health`도 원본 이동 없이 직접 응답하는지 확인합니다.

## 실제 EC2 장애 기록 — 별도 배포 결과 반영 대기

| 항목 | 실제 기록 |
| --- | --- |
| 발생 시각 / 리전 / 인스턴스 ID | 기록 대기 |
| 증상·실패 명령·종료 코드 | 기록 대기 |
| 원인 가설 | 기록 대기 |
| 검증 명령·로그·관찰 | 기록 대기 |
| 확인한 원인과 조치 | 기록 대기 |
| 동일 명령의 수정 후 결과 | 기록 대기 |
| 재발 방지와 관련 구성 | 기록 대기 |
| 증빙 파일 | 실제 로그 확보 후 연결 |

로컬 사례는 실제 수행한 보고서로 유지합니다. 담당자가 클라우드 환경의 장애 사례를 요구하면 EC2 기록까지 완성합니다. 예상 증상·계획을 실제 발생 결과로 쓰지 않습니다.

## 배포 시 진단 가이드

아래는 실제 장애 기록이 아닌 진단 순서입니다. 조사 범위는 이번 실습 EC2입니다.

| 관찰 | 가설 | 확인할 근거와 조치 방향 |
| --- | --- | --- |
| 외부 HTTP 타임아웃 | SG 80·공인 IP·IGW 경로·서브넷 연결 누락 | AWS 조회 후 필요한 실습 설정만 수정 |
| SSH 타임아웃 | 공인 IP와 SG 22 `/32` 불일치 | 현재 IP와 규칙 비교; 22 전체 공개로 우회하지 않음 |
| localhost 연결 거부 | Nginx 설치·기동·설정 실패 | 서비스·`nginx -t`·cloud-init·Nginx 로그 |
| `/health` 200, 홈 502 | 원본 DNS·TLS·HTTPS 아웃바운드 문제 | EC2 원본 HTTPS 응답과 Nginx error log |
| 로그인 HTTPS 이동 | 설계된 공개 프록시 동작 | 고정 원본·경로·쿼리 유지 확인 |
| AWS AccessDenied | action·ARN·리전·태그 조건 불일치 | 실패 작업과 정확한 자원 확인; 필요한 범위만 검토 |
| 삭제 후 재검증 실패 | 스택 삭제 뒤 잔여 조회가 일시 실패 | 생성 기록의 정확한 StackId/리소스 ID로 조회; 이름만으로 다른 자원 삭제 금지 |
